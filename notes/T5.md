# Ticket T5: The image server crashes every afternoon

## Brief Summary
- **Issue Name:** The image server crashes every afternoon
- **Issue Explanation (Brief):** In `orbit/tiles/cache.py`, when the cache exceeded `max_items`, it executed `old = self.order.pop()`, which popped from the end of the list—evicting the newly added item while letting older items persist indefinitely. Furthermore, `TileCache` counted items rather than total memory usage, ignoring `ORBIT_TILE_CACHE_MB` (default 256 MB), and `self.order.remove(k)` caused $O(N)$ slowdowns on popular scenes. Eventually, unbounded memory growth triggered the Linux Out-Of-Memory (OOM) killer.
- **Solution Explanation (Brief):** Replaced `self.items` with an `OrderedDict` for true $O(1)$ LRU caching, added tracking of `current_bytes` and memory limit enforcement based on `ORBIT_TILE_CACHE_MB` (default 256 MB), and properly evicted the oldest items via `popitem(last=False)`.

---

## What Was Seen
The tile server crashed every afternoon between 3 and 5 pm when its memory consumption grew to 8–9 GB, causing Linux kernel OOM killer to terminate the Python process (`Out of memory: Killed process 48211 (python)`). Memory only increased and never went down. Popular scenes became progressively slower during the afternoon.

## Reproduction Steps
1. Start the tiles service and monitor `GET /debug/stats`.
2. Request thousands of distinct tiles across diverse zoom levels and scenes.
3. Observe `cache_items` and `rss_mb` steadily climbing past 50,000 items and hundreds of megabytes.
4. Notice that even with cache eviction triggered, the newest items were dropped while oldest items remained unevicted.
5. Notice that `TileCache.get()` performance degraded linearly with cache size due to `self.order.remove(k)`.

## Root Cause
1. **Inverted Eviction Order:**
   - In `TileCache.put()`:
     ```python
     self.order.append(k)
     if len(self.order) > self.max_items:
         old = self.order.pop()
         self.items.pop(old, None)
     ```
   - `order.append(k)` placed the newest key at the end.
   - `order.pop()` removed from the end (index -1), discarding the newest key just added and retaining old entries forever.
2. **Ignored Memory Limit (`ORBIT_TILE_CACHE_MB`):**
   - Tile sizes vary from tens of kilobytes to hundreds of kilobytes. A hard-coded item limit of 50,000 tiles could easily exceed 7–9 GB of memory.
   - The environment variable `ORBIT_TILE_CACHE_MB` (default 256 MB) was never read or enforced.
3. **Linear Scan in `get()`:**
   - `self.order.remove(k)` searched through up to 50,000 elements on every cache hit, creating severe CPU latency in the afternoon.

## The Fix
1. In `orbit/tiles/cache.py`:
   - Utilized `collections.OrderedDict` for `self.items` to provide $O(1)$ insertion, lookup, and LRU updates (`move_to_end`).
   - Read `ORBIT_TILE_CACHE_MB` (default 256 MB) to calculate `self.max_bytes`.
   - Tracked total byte footprint in `self.current_bytes`.
   - Evicted oldest items using `self.items.popitem(last=False)` whenever `current_bytes > max_bytes` or `len(items) > max_items`.
   - Updated `get(k)` to call `self.items.move_to_end(k)` in $O(1)$ time.

## How We Know It Works
1. **Automated Test:** Added `test_t5_tile_cache_lru_and_size_capping` in `tests/test_t4_t5_t6.py`.
2. Verified that when cache limit is exceeded, the oldest entry is evicted, the accessed entry is preserved, and total memory footprint remains strictly bounded below the configured byte limit.
