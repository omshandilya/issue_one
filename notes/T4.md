# Ticket T4: Resumed downloads of large scene files are corrupted

## Brief Summary
- **Issue Name:** Resumed downloads of large scene files are corrupted
- **Issue Explanation (Brief):** The `Range` request handler in `orbit/gateway/range_proxy.py` computed the chunk length as `length = end - start`. In HTTP range requests, the byte range `bytes=start-end` is inclusive, meaning the correct chunk length is `end - start + 1`. Because 1 byte was dropped from the end of every chunk, multi-part resumed downloads resulted in truncated, corrupted files and checksum mismatches.
- **Solution Explanation (Brief):** Updated `length = end - start + 1` in `serve_file()`, added proper suffix range handling (e.g. `bytes=-500`) in `parse_range()`, and set appropriate `Content-Length` and `Accept-Ranges` headers.

---

## What Was Seen
When downloading large scene files (e.g. `GET /scenes/S1_kochi_20251012_large/file`) in pieces using HTTP `Range` headers, the reassembled file was corrupted:
- Checksum failed to match `GET /scenes/{scene_id}/checksum`.
- The final reassembled file was slightly smaller than the original on disk.
- GIS software failed to parse the file ("unexpected end of data" / "invalid TIFF").
- Single full-file downloads (without `Range`) were unaffected.

## Reproduction Steps
1. Request a file in 4 MB pieces using the `Range` header:
   - Chunk 0: `Range: bytes=0-4194303` (4,194,304 bytes requested)
   - Chunk 1: `Range: bytes=4194304-8388607` (4,194,304 bytes requested)
2. Measure the response body length of each chunk.
   - Each returned chunk had length `4,194,303` bytes (1 byte short).
3. Concatenate the chunks. The joined file was short by 1 byte per chunk, corrupting offsets and SHA256.

## Root Cause
- In `orbit/gateway/range_proxy.py`:
  ```python
  start, end = rng
  length = end - start
  data = read_range(path, start, length)
  ```
- Per RFC 7233 / RFC 9110 Section 14.1.2, HTTP byte ranges are inclusive: byte range $0-4$ includes bytes $0, 1, 2, 3, 4$ (length 5).
- Calculating `length = end - start` omitted the last byte of each range interval, causing systematic 1-byte data loss on every chunk.

## The Fix
1. In `orbit/gateway/range_proxy.py`:
   - Corrected byte length calculation to `length = end - start + 1`.
   - Enhanced `parse_range()` to properly handle suffix ranges (e.g. `bytes=-500` returning the last 500 bytes of the file).
   - Set `Content-Length: str(length)` and `Accept-Ranges: bytes` headers on partial responses (`206 Partial Content`).

## How We Know It Works
1. **Automated Test:** Added `test_t4_range_resumed_download_matches_checksum` in `tests/test_t4_t5_t6.py`.
2. Verified that downloading files in multiple chunks, reassembling them, and hashing them yields an exact match to the original file's size and SHA256 checksum.
