# Ticket T6: After a power cut, some scenes are broken or duplicated

## Brief Summary
- **Issue Name:** After a power cut, some scenes are broken or duplicated
- **Issue Explanation (Brief):** In `orbit/worker/ingest.py`, the worker recorded metadata and committed to SQLite before copying the scene file. If a power cut happened during file copy, the scene was already visible in search results, but the file was truncated on disk, causing `404 tile not found` on access. In addition, the worker generated a random UUID suffix (`f"{scene_id}-{uuid.uuid4().hex[:6]}"`), causing duplicate records to appear whenever an import was re-run to fix the broken scene.
- **Solution Explanation (Brief):** Made file writing atomic by writing to a temporary file (`.tmp`) and renaming (`os.replace`) only when complete. Delayed database insertion and commit until the file write is verified and finalized. Used the exact `scene_id` provided, and cleaned up orphaned `scene_rtree` and `scene_index` records before re-inserting in `orbit/catalog/db.py`.

---

## What Was Seen
After a power cut during ingest:
1. Two scenes appeared in search results, but requesting tiles returned "404 tile not found".
2. Files in `data/files/` were truncated (e.g. 2 MB instead of 180 MB).
3. Re-running the ingest command created duplicate scene entries in search results rather than repairing the existing ones.

## Reproduction Steps
1. Set `ORBIT_FAULT_KILL_AFTER_BYTES=50000000` (which halts the process abruptly like a power cut after writing 50 MB).
2. Execute `python -m orbit.worker.ingest <source_file> <scene_id>`.
3. The process is terminated hard with exit code 137.
4. Check database: the scene was already in `scenes` and `scene_rtree`.
5. Check file: only 50 MB was written out of 180 MB.
6. Check tiles: tile service rejected requests with 404 because file size didn't match `size_bytes`.
7. Re-run ingest: a second row was created with a different UUID suffix, producing duplicates.

## Root Cause
1. **Premature Database Commit:**
   - In `orbit/worker/ingest.py`:
     ```python
     # Make the scene visible, then copy its data in.
     dbmod.add_scene(db, f"{scene_id}-{uuid.uuid4().hex[:6]}", ...)
     db.commit()
     ```
   - Committing the database transaction before data was on disk violated atomicity.
2. **Random UUID Suffixes on Ingest:**
   - Appending random UUID hex strings meant every re-import was treated as a distinct scene.
3. **Non-Atomic File Writing:**
   - Writing directly to `final_path` left corrupted partial files upon interruption.
4. **R-Tree Index Duplicate Accumulation:**
   - `orbit/catalog/db.py` did not clean up `scene_rtree` and `scene_index` on `INSERT OR REPLACE INTO scenes`, leaking index entries on re-imports.

## The Fix
1. In `orbit/worker/ingest.py`:
   - Streamed incoming file data to a temporary file (`.tmp.{pid}`).
   - Ensured data is flushed and synced with `os.fsync`.
   - Used `os.replace` to atomically move the temporary file to `final_path`.
   - Only called `dbmod.add_scene()` and `db.commit()` AFTER the file has been successfully written and placed.
   - Used the exact `scene_id` parameter without adding random UUID suffixes.
2. In `orbit/catalog/db.py`:
   - Deleted existing entries from `scene_rtree` and `scene_index` before inserting updated index records for the same `scene_id`.

## How We Know It Works
1. **Automated Test:** Added `test_t6_interrupted_ingest_leaves_no_corrupted_or_duplicate_scenes` in `tests/test_t4_t5_t6.py`.
2. Verified that when an ingest is aborted by `ORBIT_FAULT_KILL_AFTER_BYTES`, neither the database nor the final file contains corrupted state.
3. Verified that re-running ingest completes successfully and leaves exactly one scene in the database and search results without duplicates.
